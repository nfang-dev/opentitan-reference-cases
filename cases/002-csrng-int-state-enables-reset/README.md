# Case 002: csrng internal-state read, write and halt enables after reset

| | |
|---|---|
| Module | `csrng` (cryptographically secure random number generator) |
| Settings | Per-instance enables for reading, writing and halting an instance's internal state |
| OpenTitan revision | [`0ea5236fe749`](https://github.com/lowRISC/opentitan/tree/0ea5236fe749e70ba18f56ba19c4be982ef46da7) (2026-11-03) |
| Result | Reading and halting agree with the design; writing cannot be checked (unresolved) |
| Machine-readable record | [`case.json`](case.json) |

## Question

The csrng programmers' guide says: "After reset, reading, writing and halting are enabled for all instances."
Which settings does each part of that sentence refer to, and does the design reset them as stated?

## Written requirement

`hw/ip/csrng/doc/programmers_guide.md`, section "Internal-State Save and Restore".

| ID | Line | What it says |
|---|---:|---|
| R1 | 149 | Reading requires `CTRL.READ_INT_STATE` to be `kMultiBitBool4True` and the selected instance's bit in `INT_STATE_READ_ENABLE` to be set. |
| R2 | 150 | Writing requires `CTRL.WRITE_INT_STATE` to be `kMultiBitBool4True` and the selected instance's bit in `INT_STATE_WRITE_ENABLE` to be set. |
| R3 | 153 | Halting requires the selected instance's bit in `INT_STATE_HALT_ENABLE` to be set. |
| R4 | 155 | "After reset, reading, writing and halting are enabled for all instances." |

R1 to R3 identify the setting behind each part of R4; R4 states their value after reset.

## Design

| ID | Location | What it shows |
|---|---|---|
| D1 | `hw/ip/csrng/data/csrng.hjson:58` | `NumApps` is 3, so each per-instance enable register has 3 bits. "All instances enabled" therefore means `0x7`. |
| D2 | `hw/ip/csrng/data/csrng.hjson:508` | `INT_STATE_READ_ENABLE` resets to `0x7`. |
| D3 | `hw/ip/csrng/rtl/csrng_reg_top.sv` | The `INT_STATE_READ_ENABLE` register flop has `.RESVAL (3'h7)`. |
| D4 | `hw/ip/csrng/rtl/csrng_state_db.sv:138` | `INT_STATE_VAL` returns an instance's state only if that instance's read-enable bit is set. |
| D5 | `hw/ip/csrng/data/csrng.hjson:940` | `INT_STATE_HALT_ENABLE` resets to `0x7`. |
| D6 | `hw/ip/csrng/rtl/csrng_reg_top.sv` | The `INT_STATE_HALT_ENABLE` register flop has `.RESVAL (3'h7)`. |
| D7 | `hw/ip/csrng/rtl/csrng_core.sv:567` | An instance is halted only if its halt-enable bit is set. |
| D8 | `hw/ip/csrng/data/csrng.hjson` | There is no register named `INT_STATE_WRITE_ENABLE` (nor `INT_STATE_WRITE_ENABLE_REGWEN`). |
| D9 | `hw/ip/csrng/data/csrng.hjson` | `CTRL` has no field named `WRITE_INT_STATE`. |
| D10 | `hw/ip/csrng/data/csrng.hjson:539` | `INT_STATE_VAL` is read-only for software (`swaccess: "ro"`), so there is no register path for writing internal state. |

## Which evidence is independent

The register flops in `csrng_reg_top.sv` (D3, D6) and the reset values in csrng's `registers.md` are generated by `reggen` from `csrng.hjson` (D2, D5), so their agreement is expected.
The programmers' guide is written by hand and is the independent requirement.

## Claims

| Claim | Setting | Stated (R4) | Design | Label |
|---|---|---|---|---|
| C1 | `INT_STATE_READ_ENABLE` after reset | `0x7` | `0x7` (D2, D3) | agrees |
| C2 | `INT_STATE_HALT_ENABLE` after reset | `0x7` | `0x7` (D5, D6) | agrees |
| C3 | Per-instance write enable after reset | enabled (`INT_STATE_WRITE_ENABLE`) | not present (D8, D9, D10) | **unresolved** |

## Finding

For reading and halting, the statement agrees with the design: both enable registers reset to `0x7`, and the logic uses them as described.
For writing, the guide names a control field and an enable register that do not exist at this revision, and `INT_STATE_VAL` is read-only, so the claim cannot be checked against the design.

## Missing information

Whether writing (restoring) internal state is a planned feature whose design is not yet merged, or a feature that was dropped.
The save-and-restore section of the guide was added on 2026-10-26 (lowRISC/opentitan commit `ace688c`), and csrng's register definition was changed by four commits between 2026-10-28 and 2026-11-03; at this revision it still has no write path.
The repository alone does not say which is intended, so the claim is labeled unresolved rather than as a disagreement.
No upstream change is proposed, since the documentation may describe work in progress by the block's maintainers.

## Ambiguities

- "Reading ... enabled" refers to the per-instance enable bits. Reading also requires `CTRL.READ_INT_STATE`, which resets to `kMultiBitBool4False`, so internal state is not readable immediately after reset even though the enable bits are set.

## Out of scope

- The register-write enables `INT_STATE_READ_ENABLE_REGWEN` and `INT_STATE_HALT_ENABLE_REGWEN`, which reset to 1 and are not part of the statement checked here.
- A simulation of reads from `INT_STATE_VAL` and of halting after reset.
